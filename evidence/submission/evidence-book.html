# End-to-End Request Flow

This document follows one request to:

```text
https://app.cn-project.test:8443/api/status
```

## 1. DNS Resolution

DNS server:

```text
10.7.26.228:53
```

Query:

```text
A app.cn-project.test
```

Answer:

```text
10.7.18.166
```

TTL:

```text
30 seconds
```

DNS maps the hostname to the nginx edge IP address. It does not create a connection or send the HTTP request. After DNS resolution, the client knows that `app.cn-project.test` should be reached at `10.7.18.166`. Phase 2 also lists backup DNS `10.7.18.166:53`; during controlled cutover, both DNS servers point the name to standby edge `10.7.26.228`.

## 2. TCP Connection

The client opens a TCP connection from an ephemeral local port to the nginx HTTPS listener:

```text
client ephemeral port -> 10.7.18.166:8443
```

TCP uses a three-way handshake:

```text
SYN
SYN-ACK
ACK
```

After the handshake completes, TCP provides a reliable, ordered, connection-oriented byte stream between the client and nginx.

## 3. TLS Handshake

TLS begins after the TCP connection is established. The handshake includes:

```text
ClientHello
SNI=app.cn-project.test
ServerHello
certificate
certificate verification
```

The client sends SNI so nginx can present the certificate for `app.cn-project.test`. The server certificate is signed by the local CA, and the client verifies it using the trusted public CA certificate.

The actual successful proof command is:

```bash
/usr/bin/curl --cacert .runtime/ca.crt -v https://app.cn-project.test:8443
```

The expected verification line is:

```text
SSL certificate verify ok.
```

Final proof must not use `-k`, because `-k` disables certificate verification.

## 4. HTTP Request

After TLS is established, the client sends the HTTP request inside the encrypted TLS session:

```http
GET /api/status HTTP/1.1
Host: app.cn-project.test:8443
```

In Wireshark, the HTTP request body and headers are not visible as plaintext on the wire. They appear inside encrypted TLS Application Data.

## 5. nginx Reverse Proxy / Load Balancing

nginx receives the decrypted HTTP request at the edge and forwards it to one upstream backend.

```text
Backend A -> 127.0.0.1:3001
Backend B -> 10.7.26.228:3002
```

The upstream selection uses round-robin load balancing. Repeated requests alternate between Backend A and Backend B when both are healthy. The `X-Backend` response header identifies which backend handled the request.

## 6. HTTP Caching

Both backends return cache headers:

```http
Cache-Control: max-age=60
ETag: "A-v1" or "B-v1"
```

The client can reuse a fresh cached response for up to 60 seconds. For validation, the client can send `If-None-Match` with a previous ETag. If the backend resource has not changed, the server returns:

```http
304 Not Modified
```

This proves HTTP caching behavior without sending a new response body.

## 7. Response Path

The response follows the reverse path:

```text
Backend
-> nginx
-> TLS
-> TCP
-> LAN
-> client
```

The backend generates the HTTP response, nginx forwards it through the established TLS session, TCP delivers the encrypted bytes across the LAN, and the client decrypts and displays the final HTTP result.

"""Start and stop only the project's backend processes, with owned PID files."""
import argparse
import os
from pathlib import Path
import signal
import subprocess
import time

ROOT = Path(__file__).resolve().parent.parent
parser = argparse.ArgumentParser()
parser.add_argument("action", choices=["start", "stop", "status"])
parser.add_argument("backend", choices=["a", "b"])
args = parser.parse_args()
runtime = ROOT / ".runtime"
runtime.mkdir(exist_ok=True)
name = "backend-" + args.backend
pidfile = runtime / (name + ".pid")
pid = int(pidfile.read_text()) if pidfile.exists() else None
command = subprocess.run(["/bin/ps", "-p", str(pid or 0), "-o", "command="],
                         capture_output=True, text=True).stdout
alive = str(ROOT / name / "app.py") in command
if args.action == "status":
    print(name, "running" if alive else "stopped", pid)
elif args.action == "stop":
    if alive:
        os.kill(pid, signal.SIGTERM)
    pidfile.unlink(missing_ok=True)
    print(name, "stopped")
elif alive:
    print(name, "already running", pid)
else:
    with (runtime / (name + ".log")).open("ab") as log:
        child = subprocess.Popen(["/usr/bin/python3", str(ROOT / name / "app.py")],
                                 cwd=ROOT, stdin=subprocess.DEVNULL, stdout=log,
                                 stderr=log, start_new_session=True, close_fds=True)
    time.sleep(0.4)
    if child.poll() is not None:
        raise SystemExit("Backend did not start; check " + str(runtime / (name + ".log")))
    pidfile.write_text(str(child.pid) + "\n")
    print(name, "started", child.pid)

# Phase 2 Viva Preparation

Both students should explain these from understanding, then swap machine roles
in a spoken rehearsal. Use the real evidence rather than memorizing a claim.

1. **What fails when primary DNS stops?** Only that DNS service. A flushed
   client can query backup DNS and still reach the existing edge and backends.
   An already cached name or open connection might continue without any DNS query.
2. **Why does NXDOMAIN differ from timeout?** NXDOMAIN is an actual negative
   DNS answer. Timeout means no answer arrived. Multiple resolver addresses do
   not imply retrying every negative answer against a different server.
3. **What does TTL 30 mean?** DNS data may be reused for that time by a cache.
   Our isolated client resolver showed a countdown; macOS also showed a short
   refresh delay after the nominal TTL. We recorded the observed behavior.
4. **Does DNS cutover move an existing connection?** No. Existing TCP/TLS
   connections can stay on the old edge. New connections after new resolution
   use the new address, so keep both edges serving through migration.
5. **How do we prove a different edge handled the request?** `X-Edge` is mac1
   or mac2, and upstream logs record the actual backend address and status.
   `X-Backend` identifies A or B; it does not identify the edge.
6. **How does nginx detect failure?** Passive request failures increment its
   failure state. Our settings mark a failed backend unavailable for five
   seconds and retry another backend, with a two-second connect timeout.
   No periodic active health probe is configured.
7. **Why do refusal and packet loss differ?** A TCP RST fails quickly. Silent
   drops wait for a timeout, which makes explicit upstream timeouts useful.
8. **Can we stop the whole Mac to simulate stopping A?** On Mac 2 that also
   removes primary nginx and backup DNS. The experiment stops only Backend A's
   process. Combined roles share host failures, called fate sharing.
9. **What remains a single point of failure?** The primary edge until traffic
   is manually moved; also shared LAN/router infrastructure. Standby plus DNS
   cutover is controlled recovery, not an automatic traffic failover service.
10. **What do the PF rules do?** On each backend's LAN interface, allow Mac 2's
    source IP and block other sources to the backend port. State tracks replies.
    The project uses a dedicated anchor and releases only its own PF reference.
11. **What cannot two Macs prove independently?** Backend B's unrelated-client
    rejection needs a third source IP. Mac 1's local access uses loopback, and
    Mac 2 shares the allowed edge IP. We prove A rejection, B allowed access,
    counters, and continuing HTTPS and document that limitation.
12. **Why does `--cacert` differ from `-k`?** The public CA file establishes
    trust while still verifying chain, hostname and validity. `-k` disables
    checks and is not used. Both Macs now also pass plain HTTPS with default
    trust after the approved CA installation on Mac 1.
13. **Why does `--resolve` help diagnosis?** It supplies an IP for a hostname
    while keeping the hostname for TLS/SNI and HTTP. That bypasses only DNS;
    it cannot prove the OS resolver or its cache. The final by-name tests omit it.
14. **Where are the layers visible?** DNS query/answer; TCP SYN/SYN-ACK/ACK with
    ephemeral client port and destination 8443; TLS ClientHello/SNI and
    ServerHello; encrypted records. curl exposes decrypted HTTP headers.
15. **How do we handle an injected fault?** Check scoped resolver and name,
    then TCP port, then validated TLS, then HTTP/upstream logs. State each
    observation and what it rules out before changing anything. Use the
    wrong-port and wrong-hostname drill evidence to distinguish TCP and TLS.
